The implementation ledger in `../task.md` records F1–F8 evidence, two audits, a separate final source-only review, and the six deliberately unperformed live gates. ## 3. F1 — complete asynchronous operation and shutdown design

Implement one main-loop-owned operation framework with operation ID, lifecycle generation, service unique owner, transaction identity, monotonic deadline, terminal result, and owned timers/FDs/cookies. Each continuation checks its generation and deadline before mutating state. One terminal public reply is required for success, error, cancellation, timeout, and coalesced waiters. A cancelled call can still yield a late remote side effect; dispose or retain its resource conservatively. D-Bus guidance also requires exactly one service reply per method call: [D-Bus API design](https://dbus.freedesktop.org/doc/dbus-api-design.html).

Convert UPower `Get`/`GetAll`/device enumeration/display-device reads; lid reads; GNOME SessionManager owner lookup, `Inhibit`, `Uninhibit`; login1 `Inhibit`, `CanSuspend`, `PreparingForSleep`, `Suspend`; brightness introspection/`Get`/`Set`/readback; and notifications. Inspect helpers for implicit synchronous introspection or bus calls, including constructor, startup, signals, periodic reconciliation, timer/failsafe, public methods, and stop. Register signals before asynchronous startup can acquire resources. Keep `GetState` local and bounded. State the remaining limitation from local disk, fsync, bus construction, and host scheduling rather than promising an absolute wall-clock bound.

Use named total budgets: ordinary remote call ≤3 s, aggregate power refresh ≤6 s, acquisition/preflight ≤9 s, notification ≤2 s, public mutation from admission to terminal reply ≤20 s, stop remote work ≤24 s against `TimeoutStopSec=30`, and client action calls 25 s. A subcall receives the lesser of its own timeout and the parent budget; queue time counts. Confirm `TimeoutStartSec=20` still covers startup or revise it with measured budget accounting. Retain 3 s bounded status calls. Reject overload truthfully; coalesce equivalent requests and serialize conflicting inhibitor/brightness operations. The 20 s public limit does not claim a kernel suspend finishes within it: classify post-dispatch suspend outcomes separately and never retry on uncertainty.

Build power snapshots privately, with bounded per-device concurrency and one aggregate deadline. Commit only for the current owner/generation. Any missing required evidence makes the aggregate unknown; partial readable devices cannot masquerade as complete battery evidence. Suspend preflight must await a fresh refresh and fresh lid evidence, not a cached result while work is pending. Owner replacement invalidates stale snapshots.

Use one brightness coordinator through async boundaries. Persist the journal before a write; durably distinguish a confirmed `Set` reply from a prepared write of unknown outcome; read back before declaring healthy; revalidate machine/output identity and desired target after callbacks. A timed-out write has an unknown outcome and retains recovery evidence even when an immediate read still equals the old value, because the remote write may arrive later. Include restart and legacy prepared-journal cases, and define attended recovery for unacknowledged writes. Disable/off/owner loss/stop supersede new dimming. Keep manual-change conflict behavior and settings durability diagnostics intact.

Stop begins immediately even if ordinary work is stalled: set shutdown state, invalidate ordinary operations, cancel timer/retry sources, reject new work, classify in-flight brightness writes, attempt restoration before normal inhibitor release, then release known GNOME ownership and close local FDs. For genuinely uncertain GNOME acquisition or release, close the dedicated session connection boundary as required by the existing design. Quit on completion or internal stop deadline. Handle unavailable bus, repeated stop, late cookie, late FD, late write reply, and startup failure without installing a resource after shutdown or losing an unresolved journal. Verify service, CLI, panel, and installer timeouts align with these bounds.

## 4. F2 — finish clock-evidence audit

Keep the MONOTONIC–BOOTTIME–MONOTONIC sample, finite ordered values, maximum 50 ms sample width, interval lower/upper gap, and 0.5 s proof threshold. A suspend is proven only if `current.lower - baseline.upper >= threshold`. Invalid or overlapping samples mean unavailable/ambiguous evidence; they must not erase a valid baseline, turn into zero gap, or create retrospective proof for a request that lacked a pre-request baseline.

Trace construction, timer start/expiry, automatic request dispatch/resolution, external `PreparingForSleep` entry/exit, periodic reconciliation, and wake handling. Remove remaining independent raw gap subtraction and prove every baseline update rule, including repeated ambiguous samples. Keep BOOTTIME for timer deadlines and MONOTONIC for operation deadlines. Preserve unknown-suspend blocking and one-shot timer consumption; lack of clock proof cannot authorize a second automatic suspend.

Required deterministic cases once scheduling tests are authorized: pause before/after middle clock read; the original 0.7 s false-positive; exact threshold; genuine growth; startup or request without baseline; repeated invalid samples; overlap; external preparation; and absence of false wake notification, timer cancellation, brightness cycling, or transaction resolution. **Do not run sleep functionality or scheduling tests under the user's current instruction.**

## 5. F3 and F4 — prevention ownership and acquisition outcome

Make `SetPrevention(True)` explicit for five states: (1) healthy current-owner GNOME cookie plus live login1 FD → success with no acquisition; (2) equivalent acquisition pending → join one result; (3) release pending, unknown dispatched acquisition, or inconsistent partial ownership → truthful error/recovery, no duplicate acquisition; (4) no ownership and available → one acquisition; (5) shutdown/unavailable bus → `Unavailable`. Reevaluate fresh battery/failsafe conditions even for a healthy repeated enable. `off` during acquisition wins; requested, effective, pending, and diagnostic-origin fields remain separate. Clear only superseded prevention errors.

Track GNOME acquisition separately from cleanup: not dispatched, dispatched/unknown reply, cookie received with issuing unique owner, validated, cleanup confirmed, cleanup uncertain, and owner lost. A received cookie remains a *known* acquisition even after an owner validation failure. Release it against the issuing owner; a confirmed release is not an unknown-acquisition disconnect. Preserve release-pending recovery if that cleanup is uncertain. A truly unknown dispatched call uses the dedicated connection boundary. Close every unsuccessful or late login1 FD. Any bounded retry must recheck off, stop, failsafe, owner, and generation.

Exercise pre-dispatch error, remote error, malformed cookie, owner replacement, known cookie plus failed owner validation and successful/uncertain release, late FD/cookie after cancellation, concurrent on/on, on/off overlap, partial ownership, and shutdown at each stage. Assert actual bus calls, FD closes, cookie cleanup, public response, and final requested/effective state.

## 6. F5 — effective installation contract and safe transitions

Use one absolute-path contract for effective config/data/state homes, unit, extension, CLI, and program destinations. Default and empty XDG values resolve consistently. Preflight managed-path types and unsafe paths before any deployment mutation. Query the **running** user manager's `UnitPath`; the invoking shell's `systemd-path` result alone is insufficient because it may use a different environment ([systemd-path manual](https://www.freedesktop.org/software/systemd/man/latest/systemd-path.html)). After reload require the loaded unit's exact `FragmentPath` to be the managed unit; apply the same proof to rollback. The [systemd D-Bus API](https://www.freedesktop.org/software/systemd/man/latest/org.freedesktop.systemd1.html) defines `FragmentPath` as the file from which the unit was read.

Keep the generated `XDG_STATE_HOME` unit `Environment=` and API 6 `stateHome` readiness proof, but verify the actual generated directive under systemd parsing for spaces, quotes, backslashes, percent signs, and Unicode; reject unrepresentable/control values. Validate that settings, journal, diagnostics, agent runtime, and readiness all use that exact home. Determine a previous installation's effective home from prior runtime/unit/same-user process evidence, including legacy versions; for an active legacy agent without runtime `stateHome`, require its process environment instead of treating the unit directive as effective-process proof. Never silently move a recovery journal. Reject an unprovable or unsafe path change before mutation; document an attended process that first resolves outstanding records, then changes the contract. Cover rollback after a partially switched environment.

Resolve the running same-user Shell's unique owner, PID, and effective `XDG_DATA_HOME` with bounded generation checks, reading only the relevant process environment. Confirm the `/proc` PID's UID matches the D-Bus-reported UID before reading, and recheck both unique owner and PID after extension discovery. Then prove the selected UUID is actually discovered from the intended directory and cannot be shadowed by another copy; use a supported GNOME extension path query where available and fail preflight when proof is unavailable for a custom path. GNOME documents user/system extension locations and a path-bearing extension object ([extension anatomy](https://gjs.guide/extensions/overview/anatomy.html), [extension API](https://gjs.guide/extensions/topics/extension.html)); verify how the installed Shell/tool exposes that path before depending on it. A matching environment alone is not proof of effective UUID selection. Preserve active-runtime registration as a separate post-install readiness gate; avoid changing manager-global environment or restarting Shell as a workaround.

Test default/empty and matching custom session paths, installer-only overrides, relative/unsafe paths, inaccessible `/proc`, Shell owner/PID replacement, missing extension-path proof, shadowed UUID and unit, escaped unit values, legacy/changed state homes with outstanding records, exact state/fragment mismatch, failed reload/activation, and rollback to the prior environment and fragment. All installer fixtures must stay isolated from the real user services.

## 7. F6 — dimming and recovery without redundant writes

Treat lid stay-awake, panel blanking, and GNOME monitor layout as separate outcomes. The app's `handle-lid-switch` lock addresses logind's low-level lid policy; a system-wide `HandleLidSwitch=ignore` is an administrator configuration choice, not an installer action or proof of GNOME/firmware behavior. Some laptops may blank the built-in panel independently, making software dimming unnecessary or physically unobservable. Keep F6's journal and restore safety requirements for machines where the feature is exposed, but do not make successful physical dimming a prerequisite for the main sleep-prevention feature. On attended hardware, observe whether the machine stays awake, whether the panel is physically blanked, whether an external display remains usable, and whether GNOME retains the expected monitor layout. Investigate the reported Kali Wayland closed-lid rendering/glitch behavior with exact Shell, Mutter, driver, connector, and monitor configuration before generalizing it or changing display policy. See [systemd lid configuration](https://www.freedesktop.org/software/systemd/man/latest/logind.conf.html), [systemd low-level inhibitor semantics](https://github.com/systemd/systemd/blob/main/docs/INHIBITOR_LOCKS.md), and [Mutter backend lid handling](https://gnome.pages.gitlab.gnome.org/mutter/meta/class.Backend.html).

Accept repeated enable only when the coordinator proves the owned journal is healthy: disk journal equals expected record, machine/output identity matches, and physical readback confirms the dimmed target. That path performs no restore/redim, replacement journal, setting rewrite, or new brightness write. Keep open-lid enable idempotent. Genuine recovery pending, malformed/foreign journal, identity mismatch, or uncertain write remains conservative. Explicit re-enable after a recorded manual conflict may rearm once with a fresh guarded journal. Disable during in-flight dim changes the desired target and resolves late replies through the same coordinator. Keep UI/CLI `brightnessRecoveryPending` truthful.

Verify healthy repeated enable, open lid, recovery pending, output change, manual conflict rearm, settings/journal durability failure, readback mismatch, adapter unavailable, late write, and enable/disable/stop races. Assert journal contents and write counts, not just API success.

## 8. F7 and F8 — panel registration and independent errors

Finish registration as idle/pending/succeeded/exhausted, three total attempts with 1 s and 2 s delays. Synchronous send error, async error, and timeout follow the same policy. Guard each callback/timer with lifecycle generation, unique agent owner, connection, and cancellable. The agent must accept registration only from the current GNOME Shell unique D-Bus owner, bound that lookup, and invalidate pending or stored registration when Shell ownership changes; the reported version remains cooperative. Reset on owner change or disable/re-enable; unregister and remove sources in the correct order. In particular, unregister from the same sender/version must cancel an in-flight asynchronous owner check so it cannot publish registration after disable. A timed-out registration may already have succeeded remotely, so repeated registration by the same sender/version must be idempotent. Check installer readiness against the complete retry envelope while keeping exact runtime proof distinct from disk version and enabled metadata.

Keep connection/bootstrap, registration, and user-action errors separate. Current-owner authoritative `GetState` or `StateChanged` clears only the connection error; `TimerChanged` alone does not. Registration success clears its error. An action success clears only the action error it supersedes, using a serial so old success cannot erase newer failure. Owner change/disable resets lifecycle-local errors; stale callbacks cannot alter current display or state. Preserve agent diagnostics in composed status text.

Add executable behavioral extension tests for immediate success, synchronous/asynchronous failure, retry success/exhaustion, timeout after remote success, owner replacement during retry, disable/re-enable, unregister ordering, state recovery after registration exhaustion, simultaneous error domains, reverse-order action callbacks, and displayed text. The existing Node harness has not been run because Node is absent locally: check available local runtimes first, then use a runnable local GJS/isolated harness or an explicitly reported CI gate. Syntax parsing alone is insufficient.
