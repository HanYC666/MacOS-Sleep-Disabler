# GNOME Wayland prototype

This is a per-user prototype of Sleep Disabler for GNOME Wayland on Debian-family distributions. It uses a Python agent plus a GNOME Shell extension. The agent starts with sleep prevention **off** on every fresh process start. It does not edit `logind.conf`, GNOME power settings, kernel sleep state, or system files. The code has passed local state-machine tests but has not yet been run in a Linux GNOME session.

## Install on the GNOME Wayland machine

From this directory, in a GNOME Wayland terminal:

```sh
sudo apt install python3-dbus python3-gi
sh ./install.sh
```

If the top-bar icon does not appear immediately, log out and back in, then run:

```sh
gnome-extensions enable sleep-disabler@local
```

No build step or root helper is needed. The installer validates `${PYTHON:-/usr/bin/python3}` and generates both installed launchers with that exact executable. Program files stay under `~/.local/lib/sleep-disabler-gnome`, the CLI under `~/.local/bin`, the unit under `${XDG_CONFIG_HOME:-$HOME/.config}/systemd/user`, and the extension under `${XDG_DATA_HOME:-$HOME/.local/share}/gnome-shell/extensions/sleep-disabler@local`. Run `sh ./install.sh` again to update.

`core_install.py` stages Python sources, launchers, and the unit before switching them. It validates imports, Python compilation, shell syntax, and service structure, and uses `systemd-analyze --user verify` when available. The generated service uses `Type=dbus`, `BusName=org.sleepdisabler.App`, and `TimeoutStartSec=20`. After restart, at most ten checks, one second apart, require an active service, current session-bus ownership, exact `agentRuntimeVersion`, and matching `apiVersion`; the whole readiness probe has a 70-second monotonic deadline, including calls. Individual systemctl deployment commands have a 40-second timeout. A failed core upgrade retains failed artifacts and restores prior files, enabled state, running state, and the previously healthy API through the prior interpreter; each rollback dimension is reported separately. The prior generated launcher or narrowly recognized legacy direct unit supplies interpreter identity. If it cannot be established, API restoration is explicitly unproven. Prior inactive or disabled states are preserved on rollback; unknown, masked, static, or transitional prior states are rejected before switching. Previous core artifacts remain alongside their targets as `.previous.<unique-id>` and failed copies as `.failed.<unique-id>`.

A verified core commits before panel deployment. Extension metadata, UUID, required files, and runtime/metadata version agreement are checked before switching; JavaScript syntax is checked as an ES module when Node is installed, and explicitly reported as skipped when unavailable. Node is optional. The installer verifies discovery, enabled and active lists, then requires one state snapshot with `panelRuntimeRegistered=true`, the exact compiled `panelRuntimeVersion`, and the committed agent/API versions. Panel probing also has ten attempts and a 70-second deadline; GNOME extension commands each time out after ten seconds. Shell list membership alone cannot prove that newly copied JavaScript is loaded. Runtime registration is a cooperative version/lifecycle report, not authentication against other same-user D-Bus clients. A validated first install stays in the canonical UUID directory if discovery or activation needs logout/login. A failed upgrade retains the new copy, restores the old directory/configuration, and reports whether the old runtime can be proven restored; otherwise logout/login is required. Successful upgrades retain `.sleep-disabler-previous.*` directories and failed upgrades retain `.sleep-disabler-failed.*` directories.

One inherited file lock serializes the entire core-plus-panel installation. Catchable interruption during switching uses rollback; interruption after core commit retains the working core and follows panel recovery. Before switching, both phases persist their artifact/backup paths in transaction records. SIGKILL or power loss cannot run rollback: a later installer detects an unfinished record and stops before overwriting evidence. The diagnostic names the record to inspect; it may represent partial rollback or a completed deployment whose record could not be archived. Completed records are retained with outcome suffixes. Core records are under `~/.local/lib`, and panel records are beside the UUID directory. Several separate renames are not a crash-atomic deployment. Supplied XDG paths must be absolute. A failed optional backup-archive move prints the retained path while preserving proven deployment success.

Exit `0` means exact agent/API and panel runtime proof succeeded; a visual panel check is still required. Exit `2` means the service and CLI are usable while the panel is pending or its upgrade failed. Exit `1` means core validation/deployment failed. `~/.local/bin/sleep-disablerctl` remains available after a panel-only failure. Installation restarts the agent with prevention off.

### Inspect retained installation evidence

Core transaction records use `~/.local/lib/.sleep-disabler-core-transaction.json`; panel records use `${XDG_DATA_HOME:-$HOME/.local/share}/gnome-shell/extensions/.sleep-disabler-panel-transaction.json`. Completed records have outcome/unique-ID suffixes. An unfinished record blocks another deployment. Read the named JSON record first: it identifies target, staged, and backup paths, prior presence, and prior service/configured state. Compare each retained target and backup before choosing a restoration; preserve every record and copy while any dimension remains unproven. Do not discard the record or rerun blindly. File restoration, configured enablement, running state, and API health are separate outcomes; an archived record alone does not prove all four. The installer detects interrupted transactions; it does not automatically recover from a crash.

Core commit receipts are retained at `~/.local/lib/.sleep-disabler-core-commit.<installer-pid>`. They contain the committed flag, agent runtime/API versions, and transaction ID, and are published only after core readiness. They let the shell classify interruption immediately after helper commit as exit 2. A retained receipt proves that commit boundary was reached, not that the service is still healthy now. Receipt publication failure rolls the core back; an existing receipt at the new invocation's path stops that invocation before switching. Prepared receipt files may also remain for diagnosis.

`XDG_CONFIG_HOME`, `XDG_DATA_HOME`, and `XDG_STATE_HOME` must be absolute when supplied; empty/unset values use defaults. Agent preferences and brightness recovery data use `${XDG_STATE_HOME:-$HOME/.local/state}/sleep-disabler`. Readiness rejects malformed original D-Bus report types before JSON conversion. CLI failsafe thresholds must be integers in 1–99, with invalid inputs reported as argument errors before unsigned conversion.

If any enumerated system battery cannot be read, aggregate percentage is unknown: the readable subset cannot trigger or rearm the failsafe. Positive AC remains independent recovery evidence. Synchronous panel send errors follow the same bounded retry/action recovery rules as asynchronous errors; a newer countdown signal supersedes an older state reply. D-Bus signal transport exceptions in the agent are logged without aborting committed changes or local cleanup.

Both agent bus connections explicitly disable automatic exit as soon as they are created. Cleanup handlers are installed after local state initialization and before startup settings/brightness traffic; startup connectivity is checked before and after that traffic. Session-bus loss drops local inhibitor FDs and exits with failure for systemd restart, retaining any brightness journal because its session service is unavailable. System-bus loss takes the stop path, attempting identity-safe brightness restoration through the surviving session bus before GNOME release and local FD cleanup, then exits with failure. Repeated or simultaneous loss cannot reacquire inhibitors or redim during shutdown. Real bus-loss behavior remains a live validation gate.

Brightness becomes applied/healthy only after readback exactly matches the requested target. Ignored writes, partial changes, or failed readback retain the prepared journal and recovery diagnostic. Unexpected intermediate brightness is preserved. Recovery property reads/writes, explicit introspection, SessionManager owner lookup, and uninhibit each have a three-second D-Bus timeout; method proxies disable automatic introspection. Shutdown's two possible read/write/read restoration attempts plus owner lookup and release have a 24-second remote-call budget. Filesystem work and scheduling are additional, so this is not a hard elapsed-time guarantee within the service's 30-second stop bound. Physical restoration timing remains unverified.

The user unit is wanted by and part of `graphical-session.target`; it does not order itself after that target. When target default dependencies apply, they order wanted services before target activation, so the opposite explicit ordering can conflict. Actual target definitions, GNOME session activation, imported environment, and logout cleanup remain live gates. Missing-unit first installation is accepted only when the managed unit, program, and CLI artifacts are independently absent; orphan artifacts require inspection rather than automatic replacement.

Before staging, the installer rejects symlinks (including dangling ones) and unsupported types at the managed program, CLI, and unit destinations. Inspect these entries before recovery; they are preserved rather than overwritten.

Panel transaction intent uses exclusive creation and fsync before any switch. If that write is interrupted, even a truncated record remains a blocking diagnostic; inspect it and its stage/backup paths before attempting recovery. Completed file/configuration rollback is reported separately from runtime restoration. Commit receipts coordinate the helper and shell during catchable interruption; their rename does not promise durable publication after power loss. Panel state requests and signals both supersede older in-flight snapshots, including obsolete failures.

## First test

```sh
~/.local/bin/sleep-disablerctl status
~/.local/bin/sleep-disablerctl on
~/.local/bin/sleep-disablerctl status
systemd-inhibit --list
~/.local/bin/sleep-disablerctl off
```

The second status should show `enabled: true`. `systemd-inhibit --list` should show a Sleep Disabler `sleep` block while on and no Sleep Disabler block after off. A clean off state has `desired: false`, `enabled: false`, `gnomeInhibitorState: absent`, and `gnomeReleasePending: false`. If GNOME does not confirm `Uninhibit`, off is accepted as the requested state but the call reports an error and status shows release pending. The agent retries only against the same SessionManager owner, using a dedicated one-shot timer at five-second intervals. Three total attempts include the initial call, so the disconnect fallback normally begins about ten seconds after the first ambiguous result, plus event-loop delay. It then closes its session-bus connection and exits so GNOME drops client-owned cookies; the user service restarts it with prevention off. An externally disconnected session bus also cancels the retry source, closes local inhibitor FDs, and exits for restart. Test GNOME's normal idle blank and automatic suspend with short temporary timeouts, then restore your usual timeouts. Manual Sleep may prompt or override an inhibitor depending on GNOME policy; do not use manual Sleep as the only idle test.

The top-bar menu can toggle prevention, experimental lid mode, dimming, the battery failsafe, and start/cancel 30-minute, 1-hour, or 2-hour countdowns. The prevention switch follows `desired`, so requested prevention remains on and cancellable while effective `enabled` is false. Status and the icon report effective ownership and release pending separately. Cancel follows `timerPhase=running`, including when the displayed remaining seconds are zero. Its agent connection has explicit disconnected, connecting/retrying, and connected states. Initial `GetState` has exactly three attempts: immediately, then after one and two seconds; a valid current-owner state signal cancels retry work. The extension registers its compiled runtime version on each agent owner appearance and unregisters during disable. Every action stays disabled until a current-generation `GetState` reply or `StateChanged` signal supplies authoritative state; callbacks from an earlier agent generation cannot re-enable controls. The CLI exposes the threshold, arbitrary whole-minute duration, and timer conditions:

```sh
~/.local/bin/sleep-disablerctl failsafe on 20
~/.local/bin/sleep-disablerctl failsafe off
~/.local/bin/sleep-disablerctl timer 45 --prevention-on
~/.local/bin/sleep-disablerctl cancel-timer
~/.local/bin/sleep-disablerctl lid on
~/.local/bin/sleep-disablerctl dim on
```

**A timer or failsafe can request real suspend.** Start with the switch and idle tests; use a short timer only when ready for the laptop to sleep. The failsafe checks for a present system battery, `OnBattery`, discharging state, and a percentage strictly **below** the threshold. The diagnostic `batteryDischargeState` is `discharging`, `not-discharging`, or `unknown`. UPower state 2 is discharging; charging/full/pending-charge states 1/4/5 supply positive non-discharging evidence. States 0/3/6, missing devices, and partially unreadable non-discharging sets stay unknown. Any positively discharging usable system battery makes the aggregate discharging. Unknown data does not trigger sleep and does not rearm an already triggered low-battery episode. Rearming requires positive AC, a valid percentage at/above threshold, or established non-discharging state with valid battery context; explicit failsafe configuration also rearms it. It releases this app's inhibitors before calling login1 `Suspend(false)`. One low-battery episode can dispatch at most one failsafe request, including when its D-Bus result is ambiguous; it rearms only after positive evidence that the battery condition cleared or the user explicitly changes the failsafe setting. If this app's held GNOME cookie cannot be released, the trigger is consumed, suspend is not called, and the pending-release recovery path runs without automatically repeating the suspend request.

Lid stay-awake is experimental. The agent requests a low-level logind `handle-lid-switch` lock, but GNOME may own lid policy and still suspend. Test this with the machine attended, on AC and battery, with and without an external monitor; keep it closed longer than 30 seconds. `lidRequested`, `lidLockAcquired`, and `lidOutcome` distinguish the preference, FD acquisition, and physical verification. The agent never claims physical verification automatically.

On GNOME 46–48, dimming probes the `org.gnome.SettingsDaemon.Power.Screen` **`Brightness` property** at service `org.gnome.SettingsDaemon.Power`. It enables writing only when Linux reports exactly one connected internal DRM connector (`eDP`, `LVDS`, or `DSI`) and one backlight device. The recovery journal records those identities with `/etc/machine-id` before writing zero. Immediately before restoration, the agent rereads the journal and `/etc/machine-id`, requires the persisted record to equal the in-memory record, rechecks the adapter/output identity, and restores only if the current value still equals what it wrote. A changed or unreadable identity leaves brightness and the journal untouched. This is a conservative single-panel rule, not proof that every GNOME/hardware combination maps the legacy property to the same physical panel; physical dim/restore remains a release gate. The API read/compare/write sequence is not atomic. A copied, malformed, or older schema-1 journal is retained for manual attention. Zero is the API's minimum brightness value; whether it blanks the panel depends on hardware. A retained valid record is loaded separately from any write and then handled by one desired-state coordinator after agent restart, brightness-service return, lid changes, feature changes, resume, periodic recovery, and clean stop. On a verified wake with the lid still closed and prevention plus dimming still enabled, the agent validates and restores the old journal, creates a fresh journal, and dims again. A periodic check leaves a healthy applied dim alone; after a failed operation it may restore and redim through the same validation gate. A manual brightness conflict preserves the current value and suppresses redimming until an observed open-to-closed lid transition or explicit dimming enable. Inhibitor reacquisition and an unknown-to-closed UPower recovery do not count as physical lid-close evidence. An unavailable adapter leaves the journal pending without a write. The service has `Restart=on-failure` and a 30-second normal stop timeout, so recovery is attempted while the user manager and service are available; this does not guarantee prompt restoration after logout, systemd failure, or a disabled service. `brightnessState=dimmed-owned` means a healthy intentionally applied dim and sets `brightnessRecoveryPending=false`. Prepared, restore/redim required, unreadable, or invalid records report actual recovery pending. Manual changes are preserved and reported separately. Clean stop first sets an explicit restored-brightness target and reconciles the journal before entering remote GNOME `Uninhibit`; inhibitor ownership remains truthfully enabled until released. `lidError` belongs to the lid feature and clears on disable, success, or a superseding owner result without clearing unrelated errors. Atomic JSON replacement distinguishes failures before replace from a visible replacement whose directory durability is uncertain: settings are reread to synchronize memory and publish a warning; uncertain prepared journals prevent dimming, and uncertain applied journals retain recovery state. If a pre-0.2 journal remains, restore brightness manually with GNOME controls and inspect the record before removing it; the agent will not apply an unverified old record.

GNOME 49–50's `org.gnome.Shell.Brightness` service has `SetDimming` and `HasBrightnessControl`, but no public per-panel read/write brightness property. The agent leaves manual lid dimming unavailable there rather than guessing an output or overwriting GNOME's dimming state. Main sleep prevention remains usable. Dimming must be tested separately from lid stay-awake, since a suspended machine cannot run the agent. [GNOME 49 Shell implementation](https://github.com/GNOME/gnome-shell/blob/gnome-49/js/ui/shellDBus.js), [GNOME 50 Shell implementation](https://github.com/GNOME/gnome-shell/blob/gnome-50/js/ui/shellDBus.js)

For your `[deep]` machine, record `cat /sys/power/mem_sleep` before tests. `[deep]` selects suspend-to-RAM after logind accepts a sleep request; it does not change the inhibitor call. The same transaction logic also covers `s2idle`. `PrepareForSleep(false)` can follow either a completed or failed sleep attempt, so the agent calls an interval a real suspend only when `CLOCK_BOOTTIME - CLOCK_MONOTONIC` grows by at least 0.5 seconds. An overdue countdown is canceled with a distinct proven-suspend, failed-preparation, or uncertain outcome and never requests a second suspend. An unexpired countdown keeps its original `CLOCK_BOOTTIME` deadline only while its lid/prevention conditions still hold. Missing signals are reconciled against logind's `PreparingForSleep` property and the two-clock gap. After 30 seconds of unreadable or persistently true preparation state, user-visible reporting becomes `uncertain-blocked` and an affected timer is canceled, but the suspend safety latch remains. Timer and failsafe requests stay blocked until a false property, a logind owner replacement, or independent clock-gap evidence while logind is not explicitly reporting active preparation resolves the transaction. Accepted requests that settle without observed suspend produce a distinct notification and timer outcome. Test these cases and brightness restoration after a deliberate suspend. Do not change the kernel sleep setting for this prototype.

## Sleep transaction diagnostics

Failsafe dispatch refreshes battery data again after confirmed inhibitor release, then checks it after the final logind preflight. AC, unknown discharge/charge data, threshold recovery, or failsafe disablement during release or preflight prevents dispatch. This last power check intentionally does not require effective prevention, because release has removed it. The consumed episode is not automatically retried. Preflight also rejects shutdown, transaction, inhibitor, or logind-generation changes delivered during its D-Bus reads.

`sleepPhase` reports `idle`, `requesting`, `request-pending`, `preparing`, `reconciling`, `resolving`, or `uncertain-blocked`. `sleepOutcome` reports the latest terminal or bounded state, including `proven-resume`, `failed-preparation`, `uncertain-preparation`, `accepted-no-suspend`, `request-outcome-unknown`, `logind-owner-lost`, and the persistent uncertainty reasons. `suspendRequestOutcome` separately reports `accepted`, `rejected`, `unknown`, `accepted-without-observed-suspend`, or `proven-suspend`.

The agent calls login1 only after a shared preflight confirms that no earlier transaction is unresolved, `PreparingForSleep` is explicitly false, and this app's GNOME inhibitor is either safely held by the current SessionManager owner or confirmed absent. It repeats the guard after inhibitor release immediately before `Suspend(false)`. A small allowlist of login1 and authorization errors is treated as definite rejection. Timeout, `NoReply`, disconnect, owner loss, and unrecognized D-Bus failures remain unknown because the remote method might have run; they are never retried automatically and are resolved only from signals, the property, clock evidence, or owner replacement.

## Stop or recover

```sh
~/.local/bin/sleep-disablerctl off
~/.local/bin/sleep-disablerctl cancel-timer
systemctl --user stop sleep-disabler-gnome.service
gnome-extensions disable sleep-disabler@local
```

Stopping the service closes its inhibitor FDs and asks GNOME to release its cookie. If GNOME's reply is ambiguous during shutdown, the agent closes its session-bus connection, which is the ownership boundary for that cookie. The normal service auto-restarts on failure, so a crash or bounded ordinary-off recovery also releases client-owned inhibitors and then runs brightness recovery. If an automatic restart does not happen, `systemctl --user restart sleep-disabler-gnome.service` asks the agent to process its recovery record. To disable future starts, run `systemctl --user disable sleep-disabler-gnome.service`.

## Implementation notes

- System suspend: `org.freedesktop.login1.Manager.Inhibit("sleep", …, "block")` held as a Unix FD. GNOME idle/display: `org.gnome.SessionManager.Inhibit` with flags `4|8`. Both are required before `enabled` becomes true. GNOME cookies have explicit absent, held, and release-pending states bound to the SessionManager unique owner that issued them; aggregate `IsInhibited` is never treated as ownership proof. [login1](https://www.freedesktop.org/software/systemd/man/latest/org.freedesktop.login1.html), [GNOME SessionManager](https://gnome.pages.gitlab.gnome.org/gnome-session/re04.html)
- Battery/lid: UPower system bus properties and change signals, with a 15-second reconciliation read. [UPower](https://upower.freedesktop.org/docs/UPower/)
- Timer: `CLOCK_BOOTTIME` includes time suspended. Running timers are process-scoped; a service restart cancels them. Preferences survive restart. Timer phase is independent from sleep transaction phase and follows idle → running → consumed/canceled; canceling when no timer exists is idempotent. The agent consumes a due one-shot timer before the suspend call, including when login1 rejects the request. [Linux clock_gettime](https://man7.org/linux/man-pages/man2/clock_gettime.2.html)

- Top bar: the extension adds a native panel button, calls the app's session D-Bus API, and exposes the three connection states described above. The agent remains independent of GNOME Shell. [GNOME extension guide](https://gjs.guide/extensions/overview/anatomy.html)

A closed-lid countdown refreshes lid evidence before and after inhibitor release and checks it again after final logind preflight. Open or unknown lid consumes the countdown without requesting sleep. A prevention-conditioned countdown requires effective prevention immediately before intentional release. That deliberate release does not invalidate the condition. A condition rejected before release preserves prevention; rejection afterward leaves prevention off without retry or automatic reacquisition.

GNOME 46–50 are listed in extension metadata only as an experimental prototype test range. No version has passed a live Shell lifecycle or attended hardware test, so none is claimed supported. The matrix is: 46–48 main inhibition, lid lock, timer, and brightness **unverified**; 49–50 main inhibition, lid lock, and timer **unverified**, manual dimming **unavailable**. Debian, Ubuntu, Mint, and Kali GNOME Wayland installs and `[deep]` hardware are **unverified**. If the agent fails to start, the installer exits with an error; if Shell has not discovered or activated the extension, it exits `2` and leaves the CLI available. A failed extension discovery may require a logout/login before enabling the copied extension. See [task.md](task.md) for the outstanding live gates.
