# Linux functional port: API and behavior research

Research date: 4 October 2026. This is an implementation reference for the [checklist](research_checklist.md), not a claim that every combination has been tested. All linked technical evidence is upstream documentation, source code, or an official distribution package page. The current development machine is macOS; the physical Linux tests in the checklist remain open.

## 1. Exact behavior being ported

The repository's [app state](../Sleep%20Disabler/Sleep_DisablerApp.swift), [power services](../Sleep%20Disabler/SystemServices.swift), and [feature services](../Sleep%20Disabler/FeatureServices.swift) show the current contract. The main switch saves AC and battery `pmset` sleep/display timers, sets `disablesleep=1`, sets sleep/display timeouts to zero, and later restores settings. The battery failsafe requires an internal battery drawing power, compares `percentage < threshold`, cancels prevention, then requests sleep. The lid dimmer is independently enabled, monitors lid state (with a two second fallback poll), writes main-display brightness zero on close, and restores on open/disable. The scheduler stores its duration/options, allows 0–365 days, 0–23 hours, 0–59 minutes, rejects zero duration, optionally requires closed lid or prevention still active, and sends a sleep request at expiry. An exact Linux port should preserve these observable transitions while showing independent capability states for suspend, display idle, lid, brightness, and failsafe. It cannot equate one inhibitor with all five.

## 2. Kernel, systemd, and `deep`

The [kernel sleep-state documentation](https://docs.kernel.org/admin-guide/pm/sleep-states.html) defines `/sys/power/state` and `/sys/power/mem_sleep`. `mem` in `state` enters the bracketed mode in `mem_sleep`; `s2idle` is suspend to idle, `shallow` is standby where supported, and `deep` is suspend to RAM (typically ACPI S3). Read both files without writing them; also record `/proc/cmdline` because `mem_sleep_default=` may select the default. The app should **not** change `mem_sleep`. Inhibitors are processed by logind before it invokes the kernel suspend path, so the choice of `deep` versus `s2idle` does not change which inhibition API is called. It *does* change firmware/wake/power behavior and must be included in lid, battery, timer, and resume tests. `deep` can have longer entry/resume latency and different wake sources; no API documentation proves a particular laptop will resume or preserve display state correctly. Kernel [suspend flow](https://docs.kernel.org/power/suspend-flows.html) and [PM debugging](https://docs.kernel.org/power/basic-pm-debugging.html) explain the stages and optional debugfs statistics. If present, read `/sys/kernel/debug/suspend_stats` only for diagnosis; debugfs may not be mounted or accessible.

`systemd-logind` is the **system** service exporting `org.freedesktop.login1` at `/org/freedesktop/login1`, interface `org.freedesktop.login1.Manager`. `systemd --user` is a separate per-user service manager and is not the suspend authority. The [login1 interface](https://www.freedesktop.org/software/systemd/man/latest/org.freedesktop.login1.html) and [inhibitor design](https://github.com/systemd/systemd/blob/main/docs/INHIBITOR_LOCKS.md) specify:

| Member | D-Bus signature / effect | Port use |
|---|---|---|
| `Inhibit` | `ssss → h`: `what`, `who`, `why`, `mode` → Unix FD | Hold `sleep` and, if validated, `idle`/`handle-lid-switch` with `block`; close FD to release. Pass FDs with D-Bus Unix FD passing, not integer serialization. |
| `ListInhibitors` | `→ a(ssssuu)` | Diagnostics: `what`, `who`, `why`, `mode`, UID, PID; avoid logging unrelated apps' reasons. |
| `CanSuspend` | `→ s` | Probe; handle `yes`, `no`, `na`, `challenge`, and newer inhibited results without treating it as a guarantee of suspend success. |
| `Suspend` | `b → ()` (`interactive`) | Request exact suspend with `false`; never use generic `Sleep()` for the countdown. |
| `SuspendWithFlags` | `t → ()` where implemented | Feature probe only; do not use skip-inhibitor flags. Use `Suspend(false)` as cross-version baseline. |
| `PrepareForSleep` | signal `b`: true before, false after | Observe resume/reprobe. A signal alone does not grant time to finish work; a `delay` inhibitor is needed for guaranteed preparation. |

`sleep` is a high-level block, `idle` is a different high-level block, and `handle-lid-switch` is a low-level lock that makes logind defer the physical switch to the holder. A `delay` lock only delays. Newer systemd also offers `block-weak`; its owner/root bypass semantics differ from `block`, so use `block`. Closing or losing the FD releases the lock. `Inhibit` is subject to **noninteractive polkit** authorization; distro/default policy commonly allows active local sessions, but installation cannot promise that every administrator policy does. `Suspend(false)` may also require polkit authorization and can fail if another inhibitor remains. The app must show that failure and must never use a bypass flag to defeat other apps' locks. [systemd inhibitor design](https://github.com/systemd/systemd/blob/main/docs/INHIBITOR_LOCKS.md), [login1 API](https://github.com/systemd/systemd/blob/main/man/org.freedesktop.login1.xml).

`logind.conf` has `HandleLidSwitch`, `HandleLidSwitchExternalPower`, `HandleLidSwitchDocked`, and `LidSwitchIgnoreInhibited`; high-level `sleep` blocking is not a reliable lid contract, especially with the default lid ignore behavior. Desktop daemons may already hold `handle-lid-switch`. The app must probe the current lock owners and the desktop's actual lid policy. It must not edit global `logind.conf` as a default installation step. [logind.conf](https://www.freedesktop.org/software/systemd/man/latest/logind.conf.html).

When the failsafe or timer intentionally suspends: serialize events; cancel countdown; restore brightness if owned; release all app-owned session cookies, portal requests, and login1 block FDs; await release/confirm absence in `ListInhibitors`; recheck power state for failsafe; call `Suspend(false)` with a bounded timeout; report rejection; do not reacquire prevention automatically. Other applications' inhibitors may still prevent it. A hold on `sleep` must be removed before this call. After `PrepareForSleep(false)`, refresh session/UPower/brightness/lid and recalculate timer state. With `deep`, the app process is frozen during suspend; no countdown callback fires while asleep.

## 3. Battery and lid input

The [UPower root interface](https://upower.freedesktop.org/docs/UPower/) is on the **system bus** at `org.freedesktop.UPower`, `/org/freedesktop/UPower`, interface `org.freedesktop.UPower`. Read `OnBattery`, `LidIsPresent`, `LidIsClosed` using `org.freedesktop.DBus.Properties.Get`; subscribe to `PropertiesChanged` on that path and `DeviceAdded(o)`, `DeviceRemoved(o)`. `EnumerateDevices() → ao` lists power devices; `GetDisplayDevice() → o` returns an aggregate for status UI; `GetCriticalAction() → s` reports UPower's safety action. For actual battery eligibility, inspect each [UPower Device](https://upower.freedesktop.org/docs/Device.html): `Type` (battery is 2; UPS is 3), `PowerSupply`, `IsPresent`, `State` (`2` discharging; `6` pending discharge), `Percentage`, and where available `Energy`, `EnergyFull`, `BatteryLevel`. Peripheral batteries are not laptop system power. Reject NaN/out-of-range/unknown values, absent batteries, UPS-only systems, and stale bus ownership. With multiple physical batteries, use UPower's display aggregate for a system-wide percent only after confirming it represents the present system batteries; do not take the minimum mouse/headphone percentage. Define a fixed threshold transition and a one-shot latch so duplicate signals do not queue multiple suspend calls. Re-read `OnBattery`, device state, and percentage immediately before release/request to handle an AC reconnection race. `GetCriticalAction` is informational; hardware/desktop critical shutdown may occur regardless of this app.

UPower lid reporting is a signal source, not proof that the desktop will stay awake or that a panel is physically off. On laptops where the property is absent, stale, or disagrees with input events, mark lid-dependent features unavailable until a validated fallback exists. Re-read on owner change, resume, and a slow reconciliation timer. A hardware test must observe the actual closed-lid period beyond desktop delay timers.

## 4. Session inhibition endpoints and boundaries

The [XDG Inhibit portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Inhibit.html) is on the **session bus**: `org.freedesktop.portal.Desktop`, `/org/freedesktop/portal/desktop`, `org.freedesktop.portal.Inhibit`. `Inhibit(s window, u flags, a{sv} options) → o handle`; `flags=4` is Suspend, `flags=8` is Idle, so pass `12` for both, a valid parent window handle where possible (or empty string when allowed), and `reason`/`handle_token` in options. Hold the returned request object; call `org.freedesktop.portal.Request.Close()` on its path to release. The [Request interface](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Request.html) documents `Response(u,a{sv})` for asynchronous request results generally; do **not** assume that every persistent Inhibit request emits such a completion event. Treat the returned handle and explicit close/loss of bus owner as the relevant lifecycle. The front service is `xdg-desktop-portal`; its backend is selected by [portals.conf](https://flatpak.github.io/xdg-desktop-portal/docs/portals.conf.html) and installed implementations. In a non-sandboxed app, use the native desktop adapter if that is better validated; a portal method success does not prove lid or panel behavior.

The [freedesktop ScreenSaver idle interface](https://specifications.freedesktop.org/idle-inhibit/0.1/) uses session bus `org.freedesktop.ScreenSaver`, `/org/freedesktop/ScreenSaver`, interface `org.freedesktop.ScreenSaver`, `Inhibit(s application_name, s reason) → u cookie`, `UnInhibit(u cookie)`. This is for **idle behavior**, not a system-suspend guarantee. A screen lock policy must be verified separately. The [Wayland idle-inhibit protocol](https://wayland.app/protocols/idle-inhibit-unstable-v1) creates an inhibitor associated with a `wl_surface`; the compositor can ignore it when that surface is not visible, so it cannot be the sole mechanism of a headless/tray app. X11 DPMS and XScreenSaver can be controlled on an Xorg server but are global mutable state and are often overwritten by the DE; they are fallback experiments, never evidence of reliable cross-desktop prevention. `DISPLAY` may point to XWayland under a Wayland session.

| Desired effect | API that may contribute | What success does **not** establish |
|---|---|---|
| Stop idle system suspend | login1 `sleep` block; desktop Suspend inhibitor | Display stays lit; lid action is suppressed. |
| Stop idle dim/blank/off | DE Idle inhibitor or portal Idle; in Xfce, its own inhibitor path affects DPMS | Manual lock, screen-off button, compositor policy, lid. |
| Keep running on lid close | Desktop's own policy or verified logind low-level lock | Brightness zero or external-monitor preservation. |
| Prevent explicit manual suspend | login1 block usually intercepts logind request | A DE cannot offer force/skip-inhibitor; firmware cannot bypass. |
| Keep running through critical battery | No supported guarantee | Firmware/desktop emergency policy may override. |

For service restarts, watch `org.freedesktop.DBus.NameOwnerChanged` for login1, UPower, portal, and desktop adapter. Reopen lost subscriptions/requests and publish `degraded` until reacquired. Login1 FD release on app death is automatic. Session cookies/request objects normally vanish on bus disconnect, but re-probe instead of assuming. On logout, stop by default. Never rely on a global config edit to replace a lost process-scoped inhibitor.

## 5. Desktop adapters

**GNOME (Wayland and Xorg):** [gnome-session](https://gnome.pages.gitlab.gnome.org/gnome-session/re04.html) exports session bus `org.gnome.SessionManager`, path `/org/gnome/SessionManager`, interface `org.gnome.SessionManager`. `Inhibit(s app_id, u toplevel_xid, s reason, u flags) → u cookie`, `Uninhibit(u cookie)`, `IsInhibited(u flags) → b`; `flags=4` Suspend and `8` Idle. The XID field is ignored on current GNOME, so pass zero; test runtime introspection. GNOME Settings Daemon and Shell own actual idle/display/lid decisions, so source API and live behavioral results are both needed. A GNOME Shell extension can add a panel item using [GJS Shell extension APIs](https://gjs.guide/extensions/development/creating.html); GNOME's stock panel does not provide a universal legacy tray. For a normal app indicator, the [AppIndicator extension](https://extensions.gnome.org/extension/615/appindicator-support/) must be installed **and enabled** and match Shell version. The most direct path to an always-present top bar control is a small version-matched Shell extension talking to the app over session D-Bus; keep an ordinary application window fallback.

**Cinnamon (primarily X11; Wayland experimental on Mint 22.3):** [cinnamon-settings-daemon source](https://github.com/linuxmint/cinnamon-settings-daemon/blob/master/plugins/power/csd-power-manager.c) uses `org.gnome.SessionManager` and checks `IsInhibited` for idle. It exports `org.cinnamon.SettingsDaemon.Power.Screen` at `/org/cinnamon/SettingsDaemon/Power`; source implements `GetPercentage() → u` and `SetPercentage(u) → u` for the screen, subject to runtime introspection and hardware validation. `csd-power` itself takes a logind low-level `handle-lid-switch` FD and has a **30 second** lid safety timer. Its source can release its low-level lock when external monitors are off, after which logind may handle the lid. Thus an app's high-level lock or a momentary closed-lid check is insufficient; test beyond 30 seconds with monitors on/off and AC/battery. Cinnamon has native applets/panel integration, but an AppIndicator/StatusNotifier host must still be probed.

**Plasma (Wayland and X11):** [PowerDevil policy-agent source](https://github.com/KDE/powerdevil/blob/master/daemon/powerdevilpolicyagent.cpp) exports session service/interface `org.kde.Solid.PowerManagement.PolicyAgent` at `/org/kde/Solid/PowerManagement/PolicyAgent`. Its [header](https://github.com/KDE/powerdevil/blob/master/daemon/powerdevilpolicyagent.h) defines `InterruptSession=1` and `ChangeScreenSettings=4`; `AddInhibition(u types, s appName, s reason) → u cookie`, `ReleaseInhibition` (cookie plus a C++ defaulted `retainCookie` parameter), and `HasInhibition(u) → b` are exported slots. A C++ default argument does not establish the D-Bus wire signature, so introspect the target version before invoking release. Request bitmask `5` for both kinds, then inspect `ActiveInhibitions`/`RequestedInhibitions` because user policy can reject a returned cookie. PowerDevil itself owns low-level logind key/lid locks. KDE's [screen locker source](https://github.com/KDE/kscreenlocker/blob/master/interface.cpp) forwards a ScreenSaver inhibition to PowerDevil. Prefer the portal/ScreenSaver path first, then a validated PowerDevil adapter if needed. Test separate idle dim, screen off, auto suspend, lid, and explicit Sleep paths.

**Xfce (X11 baseline; Wayland must be separately qualified):** [xfce4-power-manager XML](https://github.com/xfce-mirror/xfce4-power-manager/blob/master/src/org.freedesktop.PowerManagement.Inhibit.xml) defines session interface `org.freedesktop.PowerManagement.Inhibit`: `Inhibit(s application, s reason) → u cookie`, `UnInhibit(u cookie)`, `HasInhibit() → b`, and `HasInhibitChanged(b)`; its [manager source](https://github.com/xfce-mirror/xfce4-power-manager/blob/master/src/xfpm-manager.c) owns bus name `org.freedesktop.PowerManagement` and [inhibit source](https://github.com/xfce-mirror/xfce4-power-manager/blob/master/src/xfpm-inhibit.c) exports path `/org/freedesktop/PowerManagement/Inhibit`. Do not invoke its nonstandard `ClearInhibitors` because it affects other apps. [Power-manager source](https://github.com/xfce-mirror/xfce4-power-manager/blob/master/src/xfpm-power.c) reacts to this inhibition by inhibiting its screensaver and DPMS path; presentation mode is a related, user-controlled setting, not something this app should silently toggle. [Xfce release notes](https://github.com/xfce-mirror/xfce4-power-manager/blob/master/NEWS) document changing Wayland/output-power behavior. Introspect the target version before choosing it as an adapter. Explicit suspend may offer a force path, so the app should not promise to block every user-initiated sleep. Treat each compositor's Wayland support as unverified until end-to-end testing.

For every adapter, test both AC and battery, default and user-edited power settings, session lock, dim/blank, auto sleep, explicit sleep, lid close with/without external monitor, daemon restart, app crash, and resume. Only a successful observation allows the corresponding capability to be `verified` for that version/session/hardware family.

## 6. Brightness, countdown, startup, and controls

The [kernel backlight ABI](https://docs.kernel.org/gpu/backlight.html) exposes `/sys/class/backlight/*/{brightness,actual_brightness,max_brightness,bl_power}`; some systems have multiple nodes, `brightness=0` is not necessarily power-off, and writes may need elevated rights. Do not install a broad udev rule or privileged always-running helper by default. GNOME, Plasma, Xfce, and Cinnamon differ in user-level brightness APIs; Cinnamon's exact screen method is above, while the others need target-version introspection and a physical brightness test before committing to an endpoint. Wayland output-power protocols are compositor-specific and generally intended for a privileged power manager, not an arbitrary background client; X11 `xrandr`/DPMS also affects outputs differently and may be overridden by the DE. Never treat XWayland as Xorg system control.

Implement dimming as an optional adapter with captured device identity, original value, written value, and ownership generation. Restore only if the current value still equals the value the app wrote. On app crash, use a per-user recovery helper/watchdog or a persistent restoration journal checked at next login; log out and `SIGKILL` must be in tests. Preserve changes made by the user or power manager. Internal panel off, external display unaffected, and CPU/network process still active during a closed-lid test are three separate assertions.

Use Linux [`CLOCK_BOOTTIME`](https://man7.org/linux/man-pages/man2/clock_gettime.2.html) for elapsed countdown because it includes suspended time; `CLOCK_MONOTONIC` excludes it, and wall time can jump. Save duration and conditions, not a stale live timer; specify whether a running timer persists across process restart (the macOS app does not persist the running state). At expiry or if a condition becomes false, cancel exactly once. On resume, compare the boottime deadline immediately. The release-and-suspend ordering in §2 applies to the timer too.

Startup: use the [XDG autostart specification](https://specifications.freedesktop.org/autostart-spec/latest/) with `~/.config/autostart/<app>.desktop` for a desktop app, or a packaged `/etc/xdg/autostart` entry only if default autostart is intended. A `systemd --user` service is optional for a headless agent and must be coordinated with autostart to avoid two copies. No custom **system** service or root daemon is required for the inhibitor-based baseline **when local polkit policy permits it**. The system's own `systemd-logind.service` and `upower.service` must be running/activatable; `xdg-desktop-portal.service` and a selected backend are needed only when the portal adapter is used. A GNOME Shell extension is required only for native top-bar UI; AppIndicator support needs an enabled extension on stock GNOME.

**Proposed app-owned extension contract (not an OS API):** reserve one single-instance session-bus service, for example `org.sleepdisabler.App`, object `/org/sleepdisabler/App`, interface `org.sleepdisabler.App1`. Define `GetState() → a{sv}` (state, capability statuses/reasons, timer deadline, remaining time), `SetPrevention(b enabled) → ()`, `StartTimer(t totalSeconds, b requireLidClosed, b requirePrevention) → ()`, `CancelTimer() → ()`, and `OpenWindow() → ()`. Emit `StateChanged(a{sv} state)` after every transition and `TimerChanged(t remainingSeconds)` at a low rate only while displayed. Clamp `totalSeconds` to the macOS app's 365d/23h/59m maximum and reject zero or invalid combinations. All methods pass through the serialized state machine; the extension performs no privileged action. Verify the D-Bus sender UID matches the app user and, where exposed, its local active session; the session bus and polkit still enforce their respective boundaries. Watch `NameOwnerChanged`; on owner loss, disable extension actions and show disconnected, then call `GetState` on reconnect. The normal app window remains a fallback.

| Event to subscribe to | Immediate reaction |
|---|---|
| UPower root/device `PropertiesChanged`, `DeviceAdded`, `DeviceRemoved` | Refresh battery eligibility and lid state; evaluate the failsafe once under the serialized state machine; reconcile brightness on lid transitions. |
| login1 `PrepareForSleep(true/false)` | Record entry; on `false`, refresh all capabilities, clocks, battery, lid, and brightness before accepting another timer/failsafe action. |
| Session/system bus `NameOwnerChanged` for login1, UPower, portal, and selected desktop service | Invalidate that adapter's state; release surviving app-owned handles where possible; re-probe and reacquire with bounded backoff; publish `degraded` until recovered. |
| Portal request error, unexpected owner loss, or desktop inhibitor rejection | Mark the specific idle/suspend capability unavailable; release newly acquired companion locks so the UI cannot show full prevention. |
| `CLOCK_BOOTTIME` timer deadline or a required condition becoming false | Cancel exactly once or run the ordered release-and-suspend sequence; on resume, compare the deadline immediately. |
| GNOME extension `NameOwnerChanged` for the app service | Disable panel actions and show disconnected until `GetState` succeeds again. |

The events above follow [UPower](https://upower.freedesktop.org/docs/UPower/), [login1](https://www.freedesktop.org/software/systemd/man/latest/org.freedesktop.login1.html), [D-Bus](https://dbus.freedesktop.org/doc/dbus-specification.html), and the [portal Request API](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Request.html). Reconciliation polls are a fallback for missed device changes; they are not evidence that a desktop obeyed an inhibitor.

For a shared tray implementation, the [StatusNotifierItem specification](https://specifications.freedesktop.org/status-notifier-item/latest/status-notifier-item.html) names session service/interface `org.freedesktop.StatusNotifierWatcher` at `/StatusNotifierWatcher`, but real Plasma [uses `org.kde.StatusNotifierWatcher`](https://github.com/KDE/plasma-workspace/blob/master/xembed-sni-proxy/sniproxy.cpp) and its [interface XML](https://github.com/KDE/plasma-workspace/blob/master/xembed-sni-proxy/org.kde.StatusNotifierWatcher.xml); GNOME AppIndicator hosts commonly follow the KDE name too. Therefore probe **both** at runtime and use the interface actually exposed. An item registers through `RegisterStatusNotifierItem(s service)` and should watch `IsStatusNotifierHostRegistered`, host/item registration signals, and watcher owner changes. It exports its own item object (conventionally `/StatusNotifierItem`) with matching `org.freedesktop.StatusNotifierItem` or `org.kde.StatusNotifierItem` interface, icon/title/status/menu properties, and activation methods; a menu may use `com.canonical.dbusmenu` if the selected host requires it. A watcher with no registered host does not render a visible icon. On GNOME, the [GJS guide](https://gjs.guide/extensions/overview/imports-and-modules.html) explicitly shows `Main.panel.addToStatusArea(...)`, and the [Quick Settings guide](https://gjs.guide/extensions/topics/quick-settings.html) shows `addExternalIndicator(...)` for a toggle. Install/enable the dedicated extension explicitly, declare tested Shell versions, and retain the normal app window for recovery.

The [desktop notifications specification](https://specifications.freedesktop.org/notification-spec/latest/) defines session bus `org.freedesktop.Notifications`, `/org/freedesktop/Notifications`, interface `org.freedesktop.Notifications`, `Notify(s app_name, u replaces_id, s app_icon, s summary, s body, as actions, a{sv} hints, i expire_timeout) → u`; check `GetCapabilities()` and tolerate unavailable service. A notification before suspend may not be seen; show outcome after resume/failure when appropriate.

## 7. Distribution dependencies and diagnostics

On Debian-family systems, `systemd` supplies logind; `upower` supplies UPower; `xdg-desktop-portal` supplies the portal front end. Backend package names are `xdg-desktop-portal-gnome`, `xdg-desktop-portal-kde`, `xdg-desktop-portal-gtk`, and `xdg-desktop-portal-xapp` where available. Debian's [package index](https://packages.debian.org/search?keywords=xdg-desktop-portal&suite=trixie) and [GNOME backend package](https://packages.debian.org/trixie/xdg-desktop-portal-gnome) establish these names for Debian 13; Ubuntu's [Noble package index](https://packages.ubuntu.com/noble/gnome/) establishes its AppIndicator package. Mint and Kali inherit much of this package naming but their installed desktop defaults and available versions require per-image verification. Avoid hard dependencies on **all** portal backends or a GNOME extension. Build-language/runtime library dependencies cannot be finalized until the implementation stack is chosen. Proposed package relationship: `Depends` on the chosen runtime libraries and UPower if the failsafe is mandatory; `Recommends` on the active desktop integration/portal only when used; `Suggests` on GNOME AppIndicator host if offering SNI integration. Packaging must never overwrite user power settings during install/uninstall.

| Release | Package facts established by official indexes | Image-specific check |
|---|---|---|
| Debian 13/Trixie | [`systemd` includes `systemd-logind.service`](https://packages.debian.org/trixie/amd64/systemd/filelist); [`upower`](https://packages.debian.org/trixie/upower); [`xdg-desktop-portal-xapp`](https://packages.debian.org/trixie/xdg-desktop-portal-xapp) for Cinnamon/MATE/Xfce, plus GNOME/GTK/KDE backends in [package index](https://packages.debian.org/search?keywords=xdg-desktop-portal&suite=trixie). | Which DE and portal backend actually run. |
| Ubuntu 24.04/Noble | [`upower` 1.90.3](https://packages.ubuntu.com/noble/upower), whose [file list](https://packages.ubuntu.com/noble/amd64/upower/filelist) includes `upower.service`; `gnome-shell-extension-appindicator` appears in the [package index](https://packages.ubuntu.com/noble/gnome/). | Session type, extension enabled state, and portal implementation. |
| Ubuntu 26.04/Resolute | [`upower` 1.91.1](https://packages.ubuntu.com/resolute/upower) and [`xdg-desktop-portal`](https://packages.ubuntu.com/resolute/xdg-desktop-portal). | GNOME Shell/portal versions and host extension on the actual image. |
| Linux Mint 22.3 | Mint's [release page](https://www.linuxmint.com/rel_zena_whatsnew.php) establishes release/desktop target; Ubuntu base names are a starting point, not proof of Mint's installed package set. | Query `apt-cache policy systemd upower xdg-desktop-portal-xapp` on a Mint image; inspect Cinnamon's own portal configuration. |
| Kali rolling | [Kali Wayland guide](https://www.kali.org/docs/general-use/wayland/) establishes session options; rolling package versions can change. | Query `apt-cache policy` and service owners on the tested image; record image date. |

UPower is a hard dependency only if a fully functioning failsafe is mandatory for installation. For a capability-based package that also supports desktops without laptop batteries, make it a recommended dependency and show the failsafe unavailable if missing. The systemd/logind requirement should be enforced by runtime probe and declared package dependency only when packaging for systemd systems. The portal and its backend are optional if the native session adapter passes behavioral tests. A package manager may pull dependencies through a desktop metapackage, but the app must probe the *running* service anyway.

Read-only probes on each target: `cat /etc/os-release`, `loginctl show-session "$XDG_SESSION_ID" -p Type -p Desktop -p Active`, `systemctl status systemd-logind`, `systemctl status upower`, `busctl --system introspect org.freedesktop.login1 /org/freedesktop/login1`, `busctl --system introspect org.freedesktop.UPower /org/freedesktop/UPower`, `busctl --user list`, `busctl --user introspect ...` for the discovered session service, `cat /sys/power/state`, `cat /sys/power/mem_sleep`, and `ls /sys/class/backlight`. `loginctl`/`busctl` may be unavailable in containers or unusual systems; diagnose that rather than equating it with unsupported desktop hardware. Avoid dumping full `ListInhibitors` to public logs because reasons/UIDs can identify other users/apps.

## 8. Open proof gates

No physical Linux results have been obtained here. Before calling any combination fully supported, run the checklist's matrix on Debian 13, Ubuntu 24.04 and 26.04, Mint 22.3, and Kali current images, with GNOME, Cinnamon, Plasma, and Xfce in their available X11/Wayland sessions. At least one laptop must run selected `[deep]` and one `[s2idle]` (or the same laptop if firmware exposes both).
